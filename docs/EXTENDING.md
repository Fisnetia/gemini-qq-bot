# 扩展接口

给「想换零件的人」的契约说明：辅助模型提供方、模型侧 MCP 工具面、
管理 API 与事件出口。明确不做的东西在文末。

## 1. aux 辅助模型提供方契约

辅助层有两个模式：填好网关并启用走**网关模式**；没填或停用自动落
**agy 模式**（由一个独立的 agy 辅助会话接管全部辅助职责，与各群的
群聊主会话分开）。模式可在管理台设置页热切换，不用重启。agy 模式
不需要任何外部提供方；本节只约束网关模式的提供方。

提供方只需实现一个端点：

```
POST {AUX_BASE_URL}/v1/chat/completions     （OpenAI 兼容）
```

- **请求体**：`{model, messages: [{role: "system", ...}, {role: "user", ...}], stream: true}`。
  `model` 取配置的 `AUX_MODEL`（默认 `hy3`，可填提供方支持的任何模型名）；
  不发送 temperature 等额外参数。
- **鉴权**：`Authorization: Bearer <key>`。key 来自 `AUX_API_KEY_FILE`
  （默认 `/run/secrets/aux_api_key`）或管理台设置页写入的覆盖值；
  只进请求头，从不落日志、不回显。
- **响应**：SSE 流式返回，逐块取 `choices[0].delta.content` 拼接为全文。
  流式正文上限 1 MiB，超限判本次调用失败。
- **粘性会话头**：头名可配（`AUX_SESSION_HEADER`，默认 `X-Aux-Session`）。
  值是逻辑会话 id 加一个粗粒度时间桶，同一逻辑会话在桶内保持稳定；
  提供方可用它把同一会话钉到同一上游账号、保持前缀缓存命中。
  不理解这个头的提供方直接忽略即可，不影响正确性。
- **视觉调用**：同一端点，user 消息的 content 为分段数组：
  `[{type: "text", text: ...}, {type: "image_url", image_url: {url: "data:image/...;base64,..."}}]`，
  图片以 data URL 内联。提供方需支持 OpenAI 视觉消息格式。

五个职责，每个都是一次独立 completion，**全部失败开放（fail-open）**：
提供方超时、报错或输出不可解析时，对应职责跳过或放行，绝不阻塞
群聊主流程。

| 职责 | 输入 | 期望输出 | 失败时 |
|---|---|---|---|
| 节奏判定 | 群聊近况 | JSON 判定（放行/延后） | 放行 |
| 相关性判定 | 待判消息与上下文 | `{"relevant": bool}` | 视为相关 |
| 图片打标 | 图片与提问 | 纯文本描述 | 只留 `[图片]` 占位 |
| 记忆折叠 | 对话片段 | JSON 记忆条目 | 延后处理 |
| 泄洪摘要 | 溢出的消息流 | 纯文本摘要 | 脚本截断渲染兜底 |

每个职责的 system 提示词在源码里（`src/app`、`src/memory`）；解析器对
格式漂移有一定宽容（例如提取首个 JSON 对象），但提供方应尽量只输出
要求的内容，不要加解释文字。记忆条目会记录来源模式（网关/agy）。

## 2. MCP 工具面（模型侧）

机器人通过 MCP 把三个工具交给 agy 会话里的模型。这是模型与运行时
之间的契约：换模型、换 agent 壳时必须保持这三个工具的语义。

### `submit_reply`——唯一的回复出口

入参（必填只有前两项）：

- `turn_token`：本轮口令，照抄本轮契约卡上给的值；
- `should_reply`：本轮是否发言（只发表情也算发言）；
- `reply_text` / `reply_parts`：整段正文，或分段数组（二选一）；
- `nicknames`、`mood_update`、`topic_state`、`memory_ops`、
  `sticker_ops`、`quote_ref`、`poke_ref`：别名提议、情绪更新、话题
  标签、记忆提议、表情动作、主引用、戳一戳（各有条数/长度上限）。

语义：

- 每轮**必须调用、只调用一次、作为最后一个动作**。调用是「提交」
  不是「发送」：运行时在轮次开始时按轮武装一个口令，口令不匹配的
  提交一律拒绝——上一轮迟到的提交永远进不了新一轮。
- 合格提交先**缓冲**，轮次结束时只确认**最后一份**：轮中有新消息
  插入时，模型可以改交一份新的，旧稿被取代而不是重复发送。
- **结构校验**在本工具内完成（字段形状、上限，以及「发言时正文与
  表情至少有其一、静默时两者必须为空」）：被拒时返回可修正的原因，
  模型应在**本轮内**改交，不要另开一轮。语义校验（引用解析、别名
  映射、表情存在性）在确认时由契约校验器统一执行。
- **静默是合法结果**：`should_reply=false` 且正文/表情为空，即本轮
  不发言。

### `sticker_search`（只读）

入参 `query`（必填，情绪/场合/画面关键词）、`limit`（1–20，默认 5）。
只检索**已收编**的表情，返回句柄与文字描述；未定性的缓存表情对它
不可见，浏览不会顺手把任何表情「转正」。

### `sticker_keep`（表情库唯一写口）

入参 `hash`（图片描述里给出的句柄）、`verdict`：`self` 收进库
（之后可被 search 到并发送），`ignore` 永久拒绝。表情库全 bot 一份、
不分群；缓存与库分离，只有经这个工具收编的才进库。

## 3. 管理 API 与管理台

全部管理端点见 `docs/openapi.yaml`：`/api/v1` 是公开面，`/internal/v1`
是同一批 handler 的旧前缀（存量面板过渡用）。设置类端点（aux 配置、
轮换/降级开关、人设卡）都热生效。浏览器管理台在 `web/`，构建后由
`WEB_DIST` 托管到 `/console/`，只调用 `/api/v1`。

## 4. 事件 webhook（只做发送端）

把生命周期事件 POST 给外部系统订阅。

- **开关**：设置环境变量 `EVENT_WEBHOOK_URL` 即启用（不设 = 关）。
  `EVENT_WEBHOOK_SECRET` 可选，设置后每条投递带 HMAC-SHA256 签名。
- **投递格式**：`POST`，`Content-Type: application/json`；头
  `X-Webhook-Event: <事件名>`，有密钥时另有
  `X-Webhook-Signature: sha256=<hex>`（对原始请求体做 HMAC-SHA256）。
  正文：

  ```json
  {"event": "turn.completed", "ts": 1794000000, "group_id": "900000001",
   "detail": {"batch_id": "...", "events": 3, "retry": false}}
  ```

- **事件表**：

  | 事件 | 时机 | detail |
  |---|---|---|
  | `turn.completed` | 一批消息处理完成（已回复或主动静默） | `batch_id`、`events`（条数）、`retry` |
  | `turn.deferred` | 本批失败、但可安全重试 | 同上 |
  | `turn.failed` | 本批以未知会话状态结束，该群通道已停 | 同上 |
  | `pacing.tier_changed` | 实际生效的节奏档位变化 | `from`、`to`、`weekly_pct`、`five_hour_pct`、`stale` |

- **投递语义是尽力而为**：发送在后台任务里完成、5 秒超时、**不重试**；
  接收方慢、宕机或返回非 2xx 都不影响主流程（只留 debug 日志）。
  不能丢事件的订阅方应以管理 API 的 `/status`、`/audit` 为准对账，
  不要指望 webhook 本身可靠送达。
- **验签**（接收方）：用密钥对收到的原始请求体做 HMAC-SHA256，与
  `X-Webhook-Signature` 的 hex 值做常量时间比较。

## 5. 明确不做

插件加载、脚本引擎、热插拔、webhook 接收端（入站插件）。需要新能力
时优先走上面四条既有契约；等出现第二个真实使用方，再议扩展机制。
